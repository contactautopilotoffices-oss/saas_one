Executive Security & Architecture Report

Subject: Mobile App Architecture Refactoring Strategy: Direct Database vs. Intermediate Backend Server

Prepared for: Technology & Operations Management

Status: Architectural Recommendation for Production Deployment

1. Executive Summary

As our enterprise mobile application (saas_mobile) scales alongside our web dashboard (saas_one), we must formalize how the mobile app securely communicates with our central database.

Currently, the mobile application interacts with our database using two different models: Direct Database Calls (relying on Supabase's client-side security) and Web Server API endpoints.

This report provides a clear, non-technical comparative analysis of three architectural paths, their security implications, speed impact (latency), cost trade-offs, and an actionable roadmap to protect our company's intellectual property and customer data from security exploits.

2. The Non-Technical Analogy: How Security Works

To make this easy for stakeholders to visualize, imagine our central database as a highly secure bank vault:

Model A: Direct Database Calls (2-Tier)

We put the Vault Door directly on the public street. Anyone can walk up and touch it.

We rely entirely on a Security Guard (PostgreSQL RLS Policies) standing outside checking IDs.

If the guard makes a single logical mistake or blinks, the entire vault can be cleaned out.

Model B: Intermediate Server (3-Tier)

We build a brick wall over the vault. The public street only sees a secure bulletproof Glass Teller Window.

The customer talks to a Bank Teller (our Middle Server) at the window.

The Teller verifies their ID, walks alone into the back vault room, grabs ONLY the requested folder, and hands it back.

The public never sees the vault, never knows its dimensions, and cannot touch the vault door.

4. Architectural Deep-Dive

Option 1: Direct Client-to-Supabase Calls (2-Tier)

In this model, the mobile application queries the Supabase database directly using the public Supabase client library.

#### Non-Technical Example

An employee logs their daily checklist. The app sends a direct command to the database table sop_completion_items to mark an item as checked.

#### Advantages

  • Minimal Latency: Since there are no stops in between, data transitions almost instantly between the database and the device.
  • Simple Codebase: Very rapid features can be built because you do not have to write server routes.

#### Disadvantages & Security Risks

  • Database Exposure: If an attacker extracts the mobile app package (.apk or .ipa), they can read the code to discover table names (e.g., invoices, users), columns, and connections.
  • Human Error Catastrophe: Security depends 100% on Row Level Security (RLS) policies inside the database. If a developer accidentally makes a typo in a single database policy rule, an attacker using the public key can wipe out or download the entire table.
  • No Rate Limiting: An attacker can write a script to hammer the database directly with billions of queries, crashing the service for everyone and inflating our database billing.

Option 2: Dedicated Intermediate Server (Decoupled 3-Tier)

We construct an independent, secure backend server (using Node.js or Python) that sits entirely between the mobile app and the database.

#### Non-Technical Example

When an employee checks a checklist item, the app talks only to our secure intermediate server. The server verifies the employee's login, ensures they aren't spamming the button, checks the DB using a highly secure connection, and reports success.

#### Advantages

  • Ironclad Security: The database is invisible to the public. Hackers cannot attack what they cannot see.
  • Input Validation: The server acts as a shield. If a hacker tries to inject corrupt files or malicious scripts, the server blocks them immediately before it ever touches our database.
  • Centralized Business Logic: If checking an item also requires triggering a payment or sending a WhatsApp notification, the server coordinates all actions safely. An attacker cannot bypass the payment check.

#### Disadvantages

  • Slight Speed Stop (Latency): Because every request stops at the server before reaching the database, response times increase by a fraction of a second.
  • Higher Maintenance & Cost: We must manage, deploy, and pay for an entirely separate server infrastructure.

Option 3: Shared Web Server (`saas_one` API Routes)

Instead of building a *new* server, we route the mobile app requests through the existing Next.js API Routes (app/api/) of our web application (saas_one), hosted serverlessly on Vercel.

#### The Major Risk: The "Blast Radius" / API Breaks

If we use the same server, a web developer might change the shape of /api/tickets to fit a beautiful new web dashboard. When they deploy this change, the live mobile app on our users' phones will instantly crash because it is still expecting the old data format.

#### How We Manage This Safely (Our Implemented Strategy)

We have already written an AI Developer Directive (api_design_and_versioning_skill.md) to permanently prevent this from occurring. We use two secure strategies:

1. Strict API Versioning:

We separate mobile and web endpoints using folder directories:

  • /api/v1/checklist ➡️ Frozen endpoint used exclusively by older mobile devices.
  • /api/v2/checklist ➡️ Modernized endpoint used by the web app and newer mobile updates.

2. Graceful Fallbacks:

Our server code is programmed to handle empty fields safely (returning null or {} instead of throwing errors), protecting older app builds from crashing.

5. Architectural Recommendation

We recommend Option 3 with strict API Versioning for our current operational stage.

Why? It gives us Option 2’s premium security (completely concealing our database from hackers) and Option 1’s cost structure (Vercel serverless runs on our existing web tier, incurring $0 in new server maintenance costs).

To protect this ecosystem, we have integrated the API Design & Versioning Skill Directive directly into our repository codebase to ensure that any AI generator or team developer adheres strictly to these versioning safeguards going forward.
